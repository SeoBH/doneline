# Doneline

SI·MSP·유지보수 업체가 고객 요청(SR)을 접수·처리·보고하는 B2B SaaS입니다. NestJS + React + TypeScript + PostgreSQL 기반이며 등록 그리드는 AG Grid Community를 사용합니다.

- 구현 구조와 확정된 화면 동작: [설계문서.md](설계문서.md)

## 실행

프로젝트 루트 `D:/doneline`에서 실행합니다.

```powershell
npm.cmd ci --prefix backend
npm.cmd ci --prefix frontend
npm.cmd run build
npm.cmd start
```

이미 의존성을 정상 설치했다면 `ci`는 생략합니다. 선언 파일이나 `react`·`vite`·`typescript`를 찾지 못하면 해당 폴더의 `npm.cmd ci --include=dev --prefix frontend` 또는 `--prefix backend`로 잠금 파일 기준 의존성을 복원합니다. 백엔드 의존성을 복원할 때는 실행 중인 해당 서버를 먼저 종료해야 Windows의 네이티브 모듈 파일 잠금을 피할 수 있습니다. 백엔드가 프런트 빌드 파일도 제공하며 기본 주소는 http://127.0.0.1:3100 입니다(`.env`의 `PORT`·`APP_ORIGIN`). 같은 PC의 Cpjt 서버(3000)와 겹치지 않도록 3100을 씁니다. 해당 포트를 사용 중인 기존 서버가 있으면 중복 실행하지 않습니다. 서버 코드를 바꾼 뒤에는 다시 빌드하고 서버를 재시작합니다.

인증서 오류가 발생하는 이 PC 환경에서는 `$env:NODE_USE_SYSTEM_CA='1'`을 설정합니다. TLS 검증을 끄지 않습니다.

| 파일                                                      | 용도                                                                                         |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `.env`                                                    | DB 접속 정보, 세션 서명 키, 서버 포트와 허용 출처. 비밀값을 저장소·로그에 공개하지 않습니다. |
| `.env.example`                                            | 설정 항목의 예시.                                                                            |
| `.env.bootstrap`                                          | 최초 관리자 생성 때 발급한 로그인 정보. 현재 비밀번호와 다를 수 있습니다.                    |
| `SLACK_WEBHOOK_URL` (`.env`)                              | 운영 알림용 슬랙 Incoming Webhook 주소. 비우면 알림을 보내지 않습니다. 테스트는 항상 빈 값으로 실행합니다. |
| `backend/package-lock.json`, `frontend/package-lock.json` | 의존성 버전 고정.                                                                            |

DB 관리 접속 정보는 Git에서 제외된 `.env.db-admin`에 저장합니다. 이 파일은 현재 Windows 사용자만 읽고 쓸 수 있으며 마이그레이션·백업 작업에서 사용합니다. 앱은 `.env`의 `doneline_app` 계정을 사용합니다. 비밀번호를 문서나 소스에 복사하지 않습니다.

최초 관리자 ID는 `admin`이며 처음 로그인하면 비밀번호를 변경합니다. `npm.cmd run seed`는 빌드된 초기화 스크립트를 실행하며 기존 관리자 비밀번호를 바꾸지 않습니다.

프런트 개발 서버는 `npm.cmd run dev --prefix frontend`로 실행합니다. `/api`를 `vite.config.ts`에 지정된 백엔드 포트로 전달하므로 백엔드도 실행해야 합니다. 이 경우 `.env`의 `APP_ORIGIN`을 실제 개발 서버 출처와 맞추고 백엔드를 재시작합니다.

## 현재 기능과 사용법

- 로그인·최초 비밀번호 변경·로그아웃, DB 세션, CSRF/Origin 검사, 로그인 시도 제한.
- RESP 기반 메뉴 트리, 메뉴·화면별 버튼 권한, 권한 변경 후 캐시 갱신.
- 화면등록·메뉴등록·RESP등록의 독립 화면과 감사 로그 조회.
- 업체 무료 가입(로그인 화면 → 업체 무료 가입): 업체와 첫 관리자(`WORKSPACE_ADMIN`)를 함께 만들고 바로 로그인합니다. 가입되면 Doneline 운영 슬랙으로 업체명·코드만 알립니다.
- 고객 요청(SR): 고객사 사용자는 **고객 요청** 화면에서 본인 법인·부서로 요청을 등록하고 댓글·완료 확인·재처리 요청을 합니다. 업체 담당자는 **요청 작업함**에서 상태(접수→처리 중→확인 대기)·담당자·우선순위를 바꾸고 답변이나 고객에게 보이지 않는 내부 메모를 남깁니다. 첫 응답·처리 기한은 업체의 **SLA 설정**으로 정하며, 설정하지 않은 우선순위는 기본값(긴급 1/4시간, 높음 4/24시간, 보통 8/72시간, 낮음 24/168시간)을 씁니다. SLA 변경은 이후 등록되는 요청부터 적용됩니다. 완료(종료)는 고객 확인으로만 됩니다.
- 월간 리포트: 업체 관리자는 **월간 리포트**에서 월·고객사별 등록·처리 완료·고객 확인 완료·처리/첫 응답 SLA 준수율·평균 처리 시간·현재 진행 중 건수를 보고 **엑셀 다운로드**로 요약·요청 목록 시트를 받습니다(한국 시간 기준).
- 앱 안 알림: 헤더의 종 아이콘에 새 요청·답변·배정·고객 확인 알림이 쌓입니다. 1분마다, 그리고 창으로 돌아올 때 갱신합니다.
- 개선 요청: 헤더의 **개선 요청** 버튼으로 누구나 Doneline 운영팀에 개선 제안·오류·문의를 보냅니다(보던 화면 이름 포함, 사용자당 1시간 10건). 운영 슬랙으로 업체 코드·구분·제목이 알려지고, 운영 관리자는 **개선 요청 수신함**에서 내용을 보고 상태(접수·검토함·반영 예정·반영 완료·반영 안 함)를 바꿉니다.
- 사용성 개선(페르소나 테스트 반영): 로그인 화면은 로그인 1개를 강조하고 고객사 가입 링크로 들어오면 고객사·업체 이름과 [회원가입]만, 링크 없이 들어오면 [무료로 시작하기]만 보입니다. 업체 가입 후 자동 로그인하고, 첫 화면에 **시작하기**(고객사→법인→부서→직원→가입 링크→승인→첫 요청) 안내가 나옵니다. 고객사 사용자·관리자는 로그인하면 **고객 요청**이 바로 열립니다. 휴대폰에서는 사이드 메뉴를 ☰로 엽니다.
- 디자인: Pretendard 글꼴, SVG 아이콘, 저장=채움·삭제=빨간 테두리 버튼 위계, 옅은 그리드 머리글. 메뉴 등록 결과는 저장 시 자동 반영되므로 별도 메뉴 새로고침 버튼은 없습니다.
- 직원 비밀번호: 메일 자동 발송 전까지 사용자 등록·[비밀번호 설정 링크 만들기]가 24시간 유효 링크를 화면에 보여 주며 관리자가 복사해 전달합니다. 링크 화면은 계정 주인 이름·업체를 표시하고, 설정 후 바로 로그인합니다.
- 가입 승인: 가입 신청 1건을 체크하고 [승인]을 누르면 역할·소속 부서를 한 창에서 골라 승인·부서 지정까지 끝냅니다. 가입 신청이 오면 업체 직원에게 알림이 갑니다. 고객사등록에서 고객사를 선택하면 [가입 링크 복사]가 나타납니다.
- 알림을 누르면 해당 요청(또는 사용자등록)으로 이동합니다. 요청의 진행·완료 알림은 요청자와 그 부서의 고객사 관리자가 함께 받습니다. 재처리 요청은 사유가 필수이며 사유는 처리 이력에 남습니다.
- 입력 형식 오류는 틀린 칸을 한국어로 안내합니다. 그리드에서 입력할 수 있는 칸은 옅은 바탕으로 표시됩니다.
- 고객사·법인·부서 독립 그리드 등록, 사용자 기본정보·승인 및 법인·부서 매핑, 고객사 링크 회원가입.
- 이메일 인증·아이디 찾기·비밀번호 설정/재설정과 로컬 메일 미리보기. 실제 이메일 발송은 보류합니다.
- RESP 레벨 저장·표시(0이 최상위). 현재 승인 제한에는 사용하지 않습니다.
- 하단 탭, 우클릭 탭 닫기/전체 닫기, 토스트 알림, 사이드바 너비 조절.

화면·메뉴·RESP·고객사·법인·부서등록에서 조회 후 행추가 또는 기존 셀 편집을 합니다. 첫 열에 체크된 행만 상단 저장·삭제의 대상입니다. 신규 행의 행삭제는 화면에서만 제거하며, 저장된 행을 지우려면 상단 삭제를 사용합니다. 저장된 코드는 수정할 수 없습니다.

화면등록에서는 화면 구현 키와 8개 버튼 사용 여부를 설정합니다. 메뉴등록에서는 저장된 메뉴를 선택하고 오른쪽에서 하위 메뉴·화면, 순서·숨김·버튼 허용을 편집한 뒤 **메뉴적용**을 누릅니다. RESP등록에서는 저장된 RESP를 선택하고 시작 메뉴를 선택한 뒤 **적용**합니다. 왼쪽 저장은 오른쪽 구성을 함께 저장하지 않습니다.

저장·삭제·연결 적용이 성공하면 현재 조회 조건으로 DB를 다시 읽습니다. 체크하지 않은 신규 행과 기존 행의 미저장 수정은 모두 버리고 저장된 값만 표시합니다. 변경 요청 실패 시 입력과 체크는 유지합니다.

탭 전환은 편집을 유지합니다. 닫기·전체 닫기·조회·초기화에는 미저장 확인창이 없으며 해당 편집 내용을 버립니다. 저장·삭제·연결 적용에는 확인창이 있습니다. 새로고침은 탭 목록만 복원하며 편집값은 복원하지 않습니다.

사이드바 경계를 드래그하면 너비가 바뀌고 더블클릭 또는 Enter로 접기/복원이 가능합니다. 일반 알림은 4초, 오류는 8초 후 닫히며 마우스·포커스가 있으면 유지됩니다. 알림은 최대 3개까지 표시하고, 같은 종류·문구의 알림은 쌓지 않고 새로 갱신합니다.

## DB 구성과 마이그레이션

현재 로컬 구성은 PostgreSQL 18, `127.0.0.1:5432`, 개발 DB `doneline_dev`, 테스트 DB `doneline_test`, 앱 역할 `doneline_app`입니다. 앱 역할과 DB 관리자는 별개입니다.

새 환경에서는 관리자가 앱 로그인 역할과 두 DB를 먼저 준비합니다. `database/create-dev-db.sql`은 psql 전용 개발 DB 생성 보조 파일이며 테스트 DB와 앱 역할은 별도로 준비해야 합니다. 각 DB에 아래 마이그레이션을 번호순으로 적용하고 `database/grant-app.sql`로 권한을 부여합니다. 앱 연결 설정 후 빌드와 seed를 각 DB에 실행해 기본 관리 데이터를 준비합니다. 기존 DB에서는 적용 이력을 확인하고 미적용 단계만 실행합니다.

마이그레이션은 `node backend/migrate.cjs`로 적용합니다. `public.schema_migrations`에 없는 번호만 순서대로 실행하고 마지막에 `grant-app.sql`을 다시 적용합니다. 로컬은 루트 `.env.db-admin`의 관리 계정을, CI·서버는 `PG*` 환경변수를 씁니다. `--dry-run`은 적용할 목록만 보여줍니다. 다른 DB는 `PGDATABASE`를 지정합니다(예: 테스트 DB).

```powershell
node backend/migrate.cjs --dry-run
```

009는 사용자등록 DELETE 버튼을 사용하도록 설정합니다. 기본 ADMIN/CUSTOMER_MANAGER 메뉴에는 삭제를 허용하고, 사용자 정의 메뉴의 DELETE 권한은 시스템 운영자가 직접 설정합니다.

## 사용자 등록·가입·승인 사용법

1. SYSTEM 운영자가 **고객사등록**에서 조회 → 행추가 → 코드·명 입력 → 체크 행 저장을 합니다. 저장된 코드는 변경할 수 없으며 명칭은 수정할 수 있습니다. 행삭제는 미저장 체크 행만 제거하고 상단 삭제는 저장된 체크 행을 DB에서 삭제합니다. 연결된 하위 코드·사용자가 있으면 삭제를 거절합니다.
2. **법인등록**은 좌측 고객사를 클릭하고 우측 법인 그리드에서 편집합니다. **부서등록**은 좌측 고객사 → 중앙 법인 → 우측 부서 순서입니다. 고객사 운영자는 자기 고객사만 조회하며 개인 업무 매핑과 무관하게 자기 고객사의 코드를 관리할 수 있습니다.
3. **RESP등록**에 `SYSTEM / CUSTOMER` 접근 구분을 지정합니다. SYSTEM은 고객사 매핑 없이 전체 범위에 접근하고, CUSTOMER는 자기 고객사에 한정됩니다. 실제 기능은 기존 화면·버튼 권한으로 부여합니다. 배정 중인 RESP의 구분은 변경할 수 없습니다.
4. **사용자등록 → 기본정보·승인**에서 고객사를 선택하고 직접 등록하면 별도 승인 없이 ACTIVE가 됩니다. SYSTEM 계정은 ‘고객사 없음’을 선택합니다. 이메일을 입력하면 비밀번호 미설정 계정과 최초 설정 메일을 함께 준비합니다. 실제 발송은 보류 상태이며 링크에서 15~128자 비밀번호를 설정합니다. CUSTOMER 계정은 매핑 전까지 로그인할 수 없습니다. 기존 사용자 행을 클릭하면 오른쪽 ‘사용자정보’에 표시됩니다. 이름·이메일·연락처·주소·RESP·고객사를 수정하고 상단 저장합니다. 초기화는 선택과 입력을 비워 신규등록으로 전환합니다. 등록 고객사는 SYSTEM 운영자만 변경할 수 있고 고객사 운영자에게는 고정됩니다. 고객사 변경 시 이전 매핑을 비웁니다.
5. 고객사등록의 저장된 행을 클릭하면 `/?signup=가입토큰` 가입 링크가 표시됩니다. 토큰은 고객사마다 서버가 만든 무작위 64자 값이며 추측하기 쉬운 고객사 코드는 링크에 쓰지 않습니다. 회원가입 화면은 고객사를 표시하지 않고 서버가 링크로 고정합니다. 가입자는 기본정보만 입력합니다. RESP는 미배정 상태로 저장되며 관리자가 지정합니다.
6. 사용자등록에서 신청 행을 체크하고 **승인**합니다. RESP는 해당 행을 클릭한 뒤 사용자정보에서 지정·저장합니다. 승인 버튼은 저장된 RESP만 사용하며 별도 RESP 입력은 받지 않습니다. 미배정 계정은 RESP를 지정해야 승인할 수 있습니다. 반려·정지 계정도 승인으로 복구할 수 있으며 반려·정지·재승인은 사유가 필수입니다. 고객사 운영자는 자기 고객사의 다른 운영자 신청도 승인할 수 있으며 SYSTEM RESP는 조회·배정할 수 없습니다.
7. **법인·부서 매핑** 탭에서 좌측 사용자 선택 → 우측 상단 법인 체크 → 법인 클릭 → 하단 부서 체크 → **매핑 저장**을 합니다. 이 기능은 USER_REGISTER의 ETC4 권한입니다. 법인 하나 이상과 **각 법인별 실제 부서 하나 이상**이 있어야 로그인할 수 있습니다. 미지정 법인·부서도 원장에 실제 코드로 등록해 선택합니다. 체크를 모두 해제하고 저장하면 접근 범위가 제거됩니다.

사용자등록 기본정보·승인 탭에는 초기화·조회·저장·삭제·승인·반려·정지, 매핑 탭에는 초기화·조회·매핑 저장만 표시합니다. 그중 RESP가 허용한 버튼만 보이며 현재 선택/상태가 맞지 않으면 비활성화합니다. 매핑 초기화는 선택 사용자의 마지막 조회 매핑으로 복원합니다.

**사용자 삭제는 실제 삭제입니다.** 체크한 계정의 매핑·세션·사용자를 함께 제거하며 감사 원본은 숫자 사용자 ID로 보존합니다. 단순 가입/로그인/조회 이력은 삭제를 막지 않습니다. 다른 사용자 승인, 업무 처리 이력 또는 업무 참조가 있으면 전체 삭제를 취소하고 정지를 안내합니다. 본인 삭제와 고객사 밖 삭제는 차단합니다. 삭제된 로그인 아이디는 다시 등록할 수 있지만 새 사용자 ID가 발급되므로 과거 감사 이력과 구별됩니다.

고객사 운영자 역할은 별도 계정 플래그가 아닌 CUSTOMER RESP의 화면·버튼 권한으로 결정합니다. 첫 고객사 운영자는 SYSTEM 담당자가 직접 등록·매핑하고, 이후부터 고객사 운영자가 자기 고객사 전체의 사용자 승인·매핑을 담당합니다. 본인 계정의 기본정보 변경과 승인·정지는 다른 운영담당자에게 요청합니다. 승인과 매핑은 별도로 저장되며 매핑 변경 시 해당 사용자의 기존 세션을 종료합니다.

아이디는 시스템 전체에서 고유하며 CUSTOMER 계정은 고객사 하나에 속합니다. 이메일 계정 복구 UI는 제공하며 실제 메일 발송·SMS·Slack 연동은 아직 제공하지 않습니다. 고객사 업무 화면은 아직 없고 일반 사용자 RESP는 빈 업무 메뉴로 시작합니다. 향후 업무 CRUD에는 고객사 및 실제 매핑된 법인·부서 조건을 모두 적용해야 합니다. 시스템 범위와 기능 권한은 별개이므로 SYSTEM도 해당 기능의 화면·버튼 권한이 필요합니다.

003~005는 앞 단계의 구조를 이어받는 업그레이드 이력이므로 유지합니다. `database/verify-initial.sql`은 앱 역할로 메뉴 순환 방지와 권한 제한을 검사하고 생성한 행을 롤백합니다.

2026-09-18 확인 결과 두 DB의 app/audit 테이블·뷰 컬럼 설명은 모두 반영돼 있습니다. `public.schema_migrations`의 이력 관리 컬럼 2개는 현재 설명 대상에서 제외돼 있습니다.

## 이메일 계정 복구와 RESP 레벨

- 이메일 복구를 추가해도 기존 계정의 비밀번호는 유지합니다.
- RESP 레벨은 0~9999입니다. 0이 최상위이며 큰 숫자가 하위입니다. 동급을 허용하고 권한을 상속하지 않습니다. 초기 ADMIN=0, CUSTOMER_MANAGER=10, 그 외=100이며 신규 기본값은 100입니다. 현재 승인 제한에는 사용하지 않습니다.
- 사용자등록의 임시 비밀번호 입력은 제거했습니다. 행 클릭 → 사용자정보 수정, 초기화 → 신규등록입니다. 체크박스는 승인·반려·정지·삭제 대상을 선택합니다.
- 저장된 사용자의 ‘비밀번호 재설정 메일 준비’는 SAVE 권한으로 저장된 이메일에 링크를 준비합니다. 이메일을 변경했다면 먼저 저장해야 합니다. 기존 비밀번호는 링크를 사용하기 전까지 유지됩니다.
- 로그인 화면의 ‘아이디 찾기 / 비밀번호 재설정’에서 인증된 이메일로 요청합니다. 고객사 사용자는 고객사 가입 링크(`/?signup=…`)로 접속하고, 공통 로그인 주소는 고객사 없는 계정만 대상으로 합니다. 같은 이메일이 여러 워크스페이스에 있으면 워크스페이스마다 따로 처리합니다. 이메일 인증 재요청도 같은 화면에 있습니다.
- 가입 시 이메일 인증 메일을 준비합니다. 관리자 직접 등록/재설정 링크에서 비밀번호를 설정하면 해당 이메일 소유 확인도 완료됩니다. 이메일 미등록·미인증 계정은 사용자 직접 아이디 찾기/비밀번호 재설정이 불가능합니다. 이메일 인증 자체를 기존 로그인 조건에 추가하지는 않습니다.
- 링크는 30분·1회용입니다. 재발급, 이메일·비밀번호·고객사·RESP·승인상태 변경 시 이전 링크는 무효입니다. 승인 전 발급된 링크가 만료/무효라면 다시 요청합니다. 비밀번호 설정 완료 후 기존 세션은 종료하지만 승인 상태와 매핑은 바꾸지 않습니다.
- 실제 발송은 아직 하지 않습니다. UI에도 발송 보류로 안내합니다. SMTP/API 발송기와 재시도·반송 처리는 추후 연결하며 보류 메일을 자동 일괄 발송하지 않습니다. 만료된 링크는 반드시 재발급합니다.

개발 PC에서 메일 확인:

```powershell
node backend/mail-preview.cjs
node backend/mail-preview.cjs <메일ID>
```

첫 명령은 유효한 보류 메일 목록, 두 번째는 한 건의 수신 주소·본문·링크를 보여줍니다. 모든 워크스페이스의 메일을 봐야 하므로 행 수준 보안을 적용받지 않는 `.env.db-admin` 관리 계정으로 접속하며 운영 모드에서는 실행되지 않습니다. 링크는 계정 복구 자격이므로 공유 로그에 복사하지 않습니다. DB 보류 본문은 암호화되고 세션 비밀키 변경 시 기존 보류 메일은 재발급해야 합니다. 초기 설치의 최초 SYSTEM 관리자 생성(`seed`)은 아직 로컬 `.env.bootstrap` 절차를 사용합니다.

## 공통 코드검색 팝업 (업무 화면용 준비)

`DataGrid` 컬럼의 `lookup` 설정으로 검색 버튼을 표시할 수 있습니다. 기존 등록 화면에는 적용하지 않았으며 업무 화면을 만들 때 연결합니다. 코드·명칭을 함께 입력하면 두 조건을 모두 만족하는 항목만 표시합니다. 앞뒤 공백과 영문 대소문자는 무시하며 `%`, `_`는 와일드카드가 아닌 입력 글자 그대로 검색합니다.

행 더블클릭 또는 행 선택 후 ‘선택’으로 원래 행의 ID·코드·명칭을 한 번에 채웁니다. 취소/Esc는 원래 값을 유지합니다. 설정된 종속 컬럼은 다른 ID 선택 시에만 비우며 같은 ID를 다시 고르면 유지합니다. 선택한 행은 저장 대상으로 체크되지만 DB 저장은 업무 화면의 저장 기능에서 수행해야 합니다.

`npm.cmd run test:lookup`은 별도 테스트 화면을 Vite의 3003 포트에서 열어 Edge로 검증하고 종료합니다. DB나 개발 서버는 사용하지 않습니다. `frontend/test/lookup.html`과 `lookup.tsx`는 테스트 전용이며 운영 빌드 진입점에 포함하지 않습니다. 기존 화면에서 확인할 새 메뉴는 없습니다.

직접 체험할 샘플은 `npm.cmd run dev --prefix frontend -- --port 5173 --strictPort` 실행 후 `http://127.0.0.1:5173/test/lookup.html?sample=1`에서 확인합니다. 법인·부서 검색과 행추가를 가상 데이터로 체험하며 로그인과 DB 저장은 없습니다. 해당 법인을 선택해야 부서 검색을 사용할 수 있습니다.

## 외부 데모(Tailscale Funnel)

이 PC의 서버를 Tailscale Funnel로 공개합니다. 서버가 화면 파일도 제공하므로 주소 하나(`https://castanets.tail12e316.ts.net`, 고정)로 전부 동작하며 비용과 추가 설치가 없습니다. PC가 켜져 있고 스크립트가 실행 중일 때만 접속됩니다.

```powershell
npm.cmd run build
```

```powershell
powershell -ExecutionPolicy Bypass -File scripts/demo.ps1
```

처음 실행하면 Tailscale이 Funnel 사용 승인 링크를 보여줄 수 있습니다. 링크를 열어 이 PC(`castanets`)의 Funnel을 허용하면 됩니다. 스크립트는 `NODE_ENV=production`(HTTPS 출처·보안 쿠키), `APP_ORIGIN`(Funnel 주소), `TRUST_PROXY=1`(앞단 프록시 1개)로 서버를 실행합니다. 공개를 완전히 끄려면 아래 명령을 실행합니다.

```powershell
& 'C:\Program Files\Tailscale\tailscale.exe' funnel reset
```

데모는 개발 DB(`doneline_dev`)를 사용하며 방문자는 **업체 무료 가입**으로 자기 업체를 만들어 체험합니다. 업체 가입·개선 요청은 운영 슬랙으로 알립니다. 회사 PC·회사망에서는 실행하지 않습니다.

`deploy/pages/functions/api/[[path]].js`는 나중에 화면을 Cloudflare Pages(`doneline.pages.dev`)에 두고 API만 이 서버로 보내고 싶을 때 쓰는 선택 구성입니다(Pages 환경변수 `BACKEND_ORIGIN`=서버 주소, `TRUST_PROXY`는 경유 프록시 수에 맞춤).

## 자동 검증(GitHub Actions)

`.github/workflows/ci.yml`이 main push와 PR마다 실행됩니다. `test` 작업은 임시 PostgreSQL 18에 앱 계정·테스트 DB를 만들고 `migrate.cjs` → 빌드 → seed → `npm test`를 실행하고, `docker` 작업은 `Dockerfile` 이미지 빌드를 확인합니다. 브라우저 테스트는 Edge가 필요해 로컬에서만 실행합니다. 결과는 GitHub 저장소의 Actions 탭에서 봅니다.

## 실제 배포(Docker)

`Dockerfile`은 서버와 화면을 한 이미지로 만듭니다(실행 사용자 node, 포트 3100). DB는 관리형 PostgreSQL을 쓰고, 배포 전에 관리 계정 환경변수로 `node backend/migrate.cjs`를 실행해 미적용 마이그레이션과 권한을 적용합니다. 컨테이너 환경변수는 `PGHOST`·`PGPORT`·`PGDATABASE`·`PGUSER`·`PGPASSWORD`·`SESSION_SECRET`(32자 이상)·`APP_ORIGIN`(https)이 필수이고, 로드밸런서 뒤라면 `TRUST_PROXY`(프록시 수)와 `PROXY_ONLY_INGRESS=1`(로드밸런서 경유로만 접속 가능할 때)을 함께 둡니다. 최초 관리자는 `node backend/dist/seed.js`로 만듭니다. 이미지 빌드는 CI의 `docker` 작업이 매번 확인합니다.
